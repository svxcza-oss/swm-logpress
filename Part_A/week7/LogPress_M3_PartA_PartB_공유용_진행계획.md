# LogPress M3 진행 계획 — Part A + Part B

> 기준: 2026-09-05  
> 담당: **Part A + Part B 겸직**

이 문서는 현재까지 실제로 진행된 내용을 기준으로,  
**M3 단계로 넘어가면서 Part A와 Part B가 무엇을 해야 하는지** 간단히 정리한 문서입니다.

---

## 1. 현재까지 진행 상황

### Part A

현재 Part A는 Baseline 재현 작업을 거의 마무리하는 단계입니다.

완료한 내용:

- StreamingLLM 재현
- SnapKV 재현
- ObservedAttention 재현
- Thunderbird 로그를 1시간 단위로 나누고 모델 입력용 chunk 생성
- 토큰이 어떤 로그 줄에서 왔는지 연결
- 압축 후 어떤 로그 줄이 살아남았는지 KEEP / PARTIAL / DROP 형태로 확인

현재 진행 중:

- H2O 구조 이해 및 재현
- H2O 결과를 다른 Baseline과 같은 형식으로 정리

즉, **H2O까지 마무리하면 Part A의 M2 Baseline 작업은 거의 정리되는 상태**입니다.

---

### Part B

Part B 담당자가 나간 뒤, 팀장님(Part D)이 Thunderbird 관련 작업을 많이 진행해둔 상태입니다.

이미 진행된 내용:

- Thunderbird 전체 로그 파싱
- 하드케이스 데이터 정리
- 원문 로그 복원
- 킬스위치 실험용 데이터 구성
- Nezha 샘플 로그를 읽는 코드 작성
- 특정 원인 로그를 찾아 K지선다 문제를 만드는 간단한 실험

따라서 **Thunderbird를 처음부터 다시 처리할 필요는 없습니다.**

다만 Nezha는 아직 전체 데이터에 대해 정리가 끝난 상태는 아닙니다.

현재 Nezha는:

```text
한 샘플의 원인을 직접 지정
→ 해당 원인 로그 줄 찾기
→ 평가 문제 생성
```

수준까지 되어 있습니다.

Part B가 앞으로 해야 할 핵심은 이것을

```text
전체 장애 사례
→ 공식 원인 정보 확인
→ 실제 로그 줄과 연결
→ 평가용 데이터셋으로 정리
```

하는 것입니다.

---

## 2. M3에서 Part A가 할 일

M3의 주 담당은 Part C입니다.

Part A는 M3 구현을 직접 맡기보다는,  
**Baseline을 마무리하고 Part C의 기술 작업을 지원하는 역할**로 넘어갑니다.

### A-1. H2O 마무리

- [ ] H2O 동작 방식 이해
- [ ] Thunderbird 로그에서 H2O 실행
- [ ] 어떤 토큰이 살아남는지 확인
- [ ] KEEP / PARTIAL / DROP 결과 만들기
- [ ] SnapKV / ObservedAttention과 같은 형식으로 정리

목표:

> H2O까지 같은 기준으로 비교할 수 있으면 Baseline 작업을 마무리한다.

---

### A-2. Baseline 결과 형식 통일

각 Baseline 결과를 D가 쉽게 평가할 수 있도록 형식을 맞춥니다.

예시:

```text
방법
압축률
chunk 번호
로그 줄 번호
전체 토큰 수
남은 토큰 수
KEEP / PARTIAL / DROP
```

대상:

- StreamingLLM
- SnapKV
- ObservedAttention
- H2O

추가로, 최종 평가에 사용할 Baseline 목록도 팀에서 한 번 확정할 필요가 있습니다.

---

### A-3. Part C의 M3 작업 지원

Part C는 M3에서 다음 흐름을 구현합니다.

```text
로그 줄
→ 해당 로그 줄의 토큰 찾기
→ 남길 줄 / 버릴 줄 결정
→ 실제 KV Cache에서 삭제
```

Part A는 지금까지 kvpress Baseline을 직접 다뤘기 때문에 다음 부분을 중심으로 C를 지원하면 됩니다.

- kvpress에서 압축이 실제로 일어나는 위치 확인
- token index가 K/V 삭제로 어떻게 연결되는지 확인
- layer 번호를 기준으로 앞쪽 layer는 그대로 두고, 뒤쪽부터 압축하는 방법 확인
- kvpress 방식이 막히면 다른 방법을 조사

백업 순서:

```text
kvpress 확장
→ custom Press
→ transformers Cache 직접 제어
```

## 3. M3와 동시에 Part B가 할 일

Part B는 M3 자체를 구현하는 역할이 아닙니다.

Part C가 M3를 진행하는 동안,  
Part B는 **Nezha 평가 데이터 준비를 병렬로 진행**합니다.

### B-1. Nezha 전체 구조 확인

먼저 아래 내용을 정확히 확인합니다.

- [ ] 전체 장애 사례가 몇 개인지
- [ ] 장애 사례를 어떤 기준으로 나누는지
- [ ] 공식 root cause 정보가 어디에 있는지
- [ ] root cause가 서비스 이름인지, 로그 문장인지, 다른 형태인지
- [ ] 현재 D가 사용한 2개 사례가 전체 데이터인지, 단순 테스트용인지

이 단계가 먼저 끝나야 이후 전처리 범위를 정확히 잡을 수 있습니다.

---

### B-2. 팀장님 Nezha 코드 인수

팀장님이 만든 `k지선다.ipynb`에서 우선 아래 부분만 이해하면 됩니다.

```text
CSV 읽기
→ JSON 안의 message 추출
→ service 이름 추출
→ 로그 문장 정리
→ 원인 로그 줄 찾기
```

K지선다 문제 생성과 LLM 평가 부분은 Part D 영역이므로 Part B가 지금 깊게 볼 필요는 없습니다.

---

### B-3. 원인 정보를 실제 로그 줄과 연결

현재 코드는 원인을 직접 적어 넣는 방식입니다.

앞으로는 장애 사례별 데이터에서 원인 정보를 자동으로 불러오고, 실제 로그 줄 번호와 연결해야 합니다.

최종적으로는 아래처럼 정리되는 것이 목표입니다.

```text
장애 ID
원인 서비스
원인 설명
실제 원인 로그 줄 번호
매핑 성공 여부
```

매핑 결과는 최소한 다음처럼 나눕니다.

```text
성공
여러 후보가 있어 애매함
로그에서 찾지 못함
```

애매하거나 못 찾은 경우를 억지로 정답 처리하지 않는 것이 중요합니다.

---

### B-4. 평가용 데이터로 정리

자동 매핑 후에는 일부 장애 사례를 직접 확인해서 실제 원인 로그 줄이 맞는지 검수합니다.

그 다음:

- [ ] 개발용 데이터와 최종 평가용 데이터 분리
- [ ] 같은 장애 사례가 양쪽에 섞이지 않도록 확인
- [ ] 정답 정보는 모델 입력 로그에 넣지 않고 별도 metadata로 저장
- [ ] D가 바로 평가에 사용할 수 있도록 loader와 설명 문서 정리

Part B의 최종 결과물:

```text
Nezha 정제 데이터
+
장애별 원인 로그 줄 정보
+
개발용 / 평가용 분리
+
loader
```

## 4. A+B 겸직 시 작업 순서

현재는 Part A와 Part B를 한 사람이 같이 맡고 있기 때문에 두 작업을 동시에 크게 벌리기보다는 비중을 순서대로 바꾸는 것이 좋습니다.

### 지금

**Part A 중심**

1. H2O 마무리
2. Baseline 결과 형식 정리
3. M2 Baseline 작업 종료

**Part B는 최소 준비**

1. 팀장님 Nezha 코드 확인
2. Nezha 전체 데이터 구조 확인
3. 전체 장애 수와 root cause 정보 위치 확인

---

### M3 진행 중

권장 비중:

```text
Part A : 30~40%
Part B : 60~70%
```

**Part A**

- C의 M3 구현 지원
- kvpress / Cache 구조 확인
- 필요하면 Baseline 추가 실험

**Part B**

- Nezha 장애 목록 정리
- root cause 정보 읽기
- root cause → 실제 로그 줄 연결
- 일부 샘플 수동 검수

---

### M3 이후

Part C의 PoC가 정상 동작하면 Part A 지원 비중을 더 줄이고 Part B에 집중합니다.

Part B는 최종적으로:

```text
전체 Nezha 장애 전처리
→ 원인 로그 줄 매핑
→ 검수
→ 개발용 / 평가용 분리
→ D에게 전달
```

까지 마무리합니다.
