# 회의록 — 목요일 회의

## 1. 핵심 문제 제기: 앵커를 "마지막 로그"로 잡는 게 맞나?

- 기존 **동헌님 코드는 앵커를 "파일에서 가장 마지막에 입력되는 로그 한 줄"**로 잡음.
- 근데 마지막 줄이 앵커가 되는 건 말이 안 됨. 실제 기업 RCA는 **"장애가 가장 먼저 나타났다고 의심되는 로그"**를 찾으려 함.
- 입력되는 로그 자체가 사람이나 모니터링 프로그램으로 **어느 정도 선별된 로그들**임 → 앵커도 그런 식으로 **선별**해야 함.
- 이 선별 방식에 **"이벤트 알람 방식"**이라는 이름을 붙여봄 (※ 실제로 있는 시스템이 아니라 임시로 붙인 이름).

## 2. 데이터셋별 앵커 기준이 다름

| | Nezha | Thunderbird |
|---|---|---|
| 성격 | CPU 오버클럭 유도로 **일부러 만든 장애** 데이터셋 | 장애(failure)가 아니라 **이상로그** |
| 원인 | 원인 로그는 남아 있음 | — |
| 문제 | **"장애 시작 의심 로그셋"이 명시 안 됨** (원인은 알아도 시작점 모름) | — |
| 보존율 정의 | — | **압축 후 이상로그 / 전체 이상로그** (원인 보존율 ❌, **이상로그 보존율**) |
| 알람 기준 | 응답지연 등 **평균과 다른 정도**로 이상 판별 | **이상로그가 유난히 밀집된 구간**을 알람 시점으로 |

## 3. "알람"의 원리와 실시간성 문제

- **원리:** 데이터셋을 시간순으로 읽으며 "이 구간이 다른 구간보다 유난히 실패율/이상률이 높네?"를 감지.
- **실시간성 Q:** 알람 자체가 실시간이 아닌데 정보를 어떻게 실시간으로 남기나?
  - → 기업은 장애 유형마다 알람 코드를 다 만든 게 아님. **여러 장애에서 공통으로 나타나는 특징을 보는 모델**을 운영.
  - → **기업 알람 시스템의 "감지 공식"만 가져와서**, 우리 정제된 데이터셋에 맞게 **변환**하면 됨. ("무슨 기준으로 알람이 발생하는가"는 그대로 가져올 수 있음.)
- **압축기가 메인, 알람은 부가기능** — 앵커를 용이하게 선정하기 위한 보조 도구.

## 4. 앵커 정의 (결론)

- 앵커 = **코드 마지막 로그 ❌ → 장애 발생을 발견한 시점 ⭕**
- Thunderbird는 장애가 아니니까 → **이상로그가 집중 발생한 시점**을 앵커로.
- **이 앵커를 기준으로 최근성(recency)을 둔다.**
- 즉 **앵커 = "최근성을 어떤 로그 기준으로 둘 것이냐"의 기준점.**

## 5. 중요도 비중 (첨부 이미지)

| 신호 | 비중 |
|---|---:|
| 최근성 | **60%** |
| 구조적 유사도 | 20% |
| Attention | 15% |
| 식별자 유사도 | 5% |

- **"이 비율 그대로?"** → 일단 **앵커 정의가 더 중요**해서 비율은 크게 상관없음.
- 처음엔 최근성 60%가 너무 높다 생각했는데, **해보니 장애 발생은 최근성으로 찾는 게 확률이 더 높을 수도** 있음.
- **"뭐가 더 중요한지 실험한 거 아닌가?" → 동헌님에게 확인.**

## 6. 방향 제안

- 아이디어는 괜찮으나 **직접 실험해서 쓸 수 있는 근거**를 찾아야 함.
- **"위치기반 + 어텐션"이 나을 것 같음 → 동의.**
- **Part D 참고 가능.** 위치기반(알람이든 위치든 기준 타임스탬프든)으로 구한 앵커를 가지고 진행.

## 7. 일정 / 협업

- 이번주 내 가능? 한다면 **코드를 직접 짜면 안 될 것 같음**(시간). 주말에 시간은 낼 수 있음.
- 동헌님도 같이 → 한 명 더 붙는다고 시간이 줄지는 미지수. **코드 나눠 짜는 협업 방식 고민 필요.**
