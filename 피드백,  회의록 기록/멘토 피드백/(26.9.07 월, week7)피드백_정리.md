# 멘토 피드백 정리 (A · C · D)

## A — 압축률 실험 (변이 통제 문제)

**핵심 지적**
- 압축률 결과가 **소수점 첫째 자리까지 똑같이** 나옴 → 이건 신호가 아니라 **변이 통제가 안 된 것.**
- 숫자가 이렇게 동일하면 사실상 **의미 없는 실험**이고, 여기서 결론을 내리는 건 위험하다.
- 압축률 결과에만 매몰된 인상 → 다시 생각해볼 것.

**방향 제안**
- 로직을 수정할 필요가 있어 보임.
- 라인을 더 잘게 쪼개거나, 다른 접근을 고민해볼 것.
- 완전한 수정보다는 **먼저 고민**부터.

**따라오는 질문**
- 왜 코드를 그렇게 짰나? / 이 테스트가 의미가 있나? / 압축 방식을 먼저 이해해야 함.

## C — 코드 품질 · 구조체 · 테스트

**구조체(TokenInfo) 사용**
- span을 리스트로 받는데, **구조체로 선언하면 더 깔끔**하고 협업에 유리.
- 리스트는 뭐가 들어가는지 안 보여 직관적이지 않음 → 남이 수정할 때 어려움.
- 파이썬은 리스트에 여러 타입이 들어가는 게 장점이지만, **가장 좋은 건 뭐가 들어가는지 명확히 보이게** 하는 것.

**필드 설계 (정보 중복 주의)**
- TokenInfo에 **token_id가 중복**으로 보임 — token_id만 있으면 나머지도 다 알 수 있는데 위치까지 중복.
- 확인용이면 몰라도, **필드는 정보가 많을수록 불리** → token_id는 빼는 것을 고려.
- 구조체 설계엔 항상 **tradeoff**(깔끔 ↔ 복잡)가 있고, 이런 결정을 **빠르고 정확하게** 내리며 개발할 것.

**테스트 우선 (TDD) — 가장 강조**
- 개발은 **테스트를 먼저 짜야 함.** 다양한 엣지 케이스 테스트를 먼저 만들고 돌려서, **테스트가 실패하는 걸 먼저 확인.**
- 구현을 제대로 했는데 테스트가 바로 성공하면 → 그 테스트가 잘못 만들어진 것.
- **코드는 자산이 아니지만 테스트는 자산.** 믿을 수 있는 건 테스트.
- 버그 발생 시: 롤백 → **에러 재현** → 원인 파악 → **테스트로 추가.** 그래야 같은 버그가 다시 안 난다고 확신 가능. → 테스트가 곧 개발자의 노하우.
- 특히 **매핑·알고리즘 코드**에서 매우 중요.

## D — KPI(지표) 설계는 '의도'가 보여야 함

**핵심**
- KPI는 **의도를 보고 세워야** 함. 랭킹 주지표 하나만이 아니라, **모든 지표에 의도가 드러나야** 함.

**각 지표마다 답해야 할 것**
- ① **왜 필요한가** — 요구사항을 얼마나 평가하기 위해 세운 것인가.
- ② **왜 그 방법인가** — 세웠다면 왜 이 방법을 골랐는가.
- ③ **의도를 충족했는가** — 그 지표가 실제로 목적을 달성하는지도 검사.
- 쓴 숫자는 **바로 근거를 댈 수 있어야** 하고, 합리적이면 괜찮음.

## 공통 메시지 (멘토 역할)

- 코멘트를 다는 이유는 **버그가 안 나도록, 가져야 할 태도·방법**을 알려주려는 것.
- 코드량이 많아지면 일일이 코멘트를 못 달아주니, 이런 원칙을 **지금 익혀둘 것.**
