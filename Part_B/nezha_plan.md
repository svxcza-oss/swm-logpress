# Part B — Nezha 데이터셋 작업 계획

## 1. 내가 맡은 일

**Nezha 장애 로그와 공식 원인 정보를 연결해, LogPress 평가에 사용할 정답지(GT)를 만든다.**

- **장애 로그:** 실제 시스템에서 발생한 로그 기록 (문제지)
- **공식 원인 정보:** 어떤 장애가 왜 발생했는지 알려주는 자료 (정답의 근거)
- **GT(Ground Truth):** 실제 원인·증거에 해당한다고 확인한 로그 줄 번호 (평가용 정답지)

Part D 팀장님은 샘플 CSV를 읽고 K지선다 문제를 만드는 코드를 작성했다. **전체 장애 사례에 대한 원인 로그 줄 정리는 별도로 확인하고 진행한다.**

## 2. 앞으로 할 작업 5가지

| 순서 | 해야 할 일 | 결과물 |
|---|---|---|
| **1** | Nezha 원본 로그와 공식 정답 파일을 확보하고 구조 확인 | 파일 목록과 데이터 구조 정리 |
| **2** | 장애 사례 1개를 골라 공식 원인과 실제 로그 줄 연결 | 샘플 1개의 GT |
| **3** | 검증한 방법을 나머지 장애 사례에도 자동 적용 | 장애별 GT 목록 |
| **4** | 애매하거나 못 찾은 결과를 구분하고 일부 직접 검수 | 신뢰할 수 있는 GT 데이터 |
| **5** | 개발용 / 최종 평가용 데이터를 나누고 읽는 코드 정리 | Part D에 전달할 데이터셋과 loader |

## 3. 순서대로 무엇을 하면 될까?

### ① 원본 데이터 구조 확인

- [ ] 팀장님께 Nezha 전체 로그 파일과 공식 원인 정보의 위치 확인
- [ ] 장애 사례가 총 몇 개인지 확인
- [ ] 파일 형식(CSV, JSON 등)과 주요 컬럼 확인
- [ ] 장애 사례와 원인 정보가 어떤 기준으로 연결되는지 확인

**완료 기준:** 각 파일이 무엇을 담고 있는지 설명할 수 있다.

### ② 장애 사례 하나로 연습

- [ ] 로그 파일 1개를 읽는다.
- [ ] 공식 자료에서 해당 장애의 원인을 확인한다.
- [ ] 원인 또는 증거에 해당하는 실제 로그 줄을 찾는다.
- [ ] 줄 번호와 판단 근거를 기록한다.

**완료 기준:** 장애 하나의 GT를 직접 만들고 왜 그 줄이 정답인지 설명할 수 있다.

### ③ 전체 장애로 자동화

- [ ] 팀장님의 `k지선다.ipynb`에서 CSV/JSON 읽기 코드를 참고한다.
- [ ] 사람이 원인 문자열을 직접 입력하는 부분을 공식 원인 정보 읽기로 바꾼다.
- [ ] 모든 장애 사례에 같은 처리를 반복한다.

**완료 기준:** 각 장애에 대해 원인 정보, 후보 로그 줄, 매핑 상태가 저장된다.

### ④ 애매한 결과 구분 및 검수

- [ ] `success`: 근거를 확인하여 정답 줄을 특정할 수 있음
- [ ] `ambiguous`: 후보가 여러 개이거나 확정 근거가 부족함
- [ ] `not_found`: 로그에서 대응되는 줄을 찾지 못함
- [ ] 일부 결과를 원본 로그와 대조해 직접 확인한다.

**완료 기준:** 확인되지 않은 줄을 억지로 정답으로 처리하지 않는다.

### ⑤ 평가용 데이터 정리

- [ ] 같은 장애 사례가 개발용과 최종 평가용에 동시에 들어가지 않게 분리한다.
- [ ] 원인 정답은 모델에 입력할 로그와 별도 파일에 저장한다.
- [ ] Part D가 데이터를 읽을 수 있도록 loader와 간단한 사용법을 작성한다.

**완료 기준:** Part D가 장애 로그와 GT를 바로 불러와 평가할 수 있다.

## 4. 최종 정답지는 어떤 모습일까?

아래는 **형식을 설명하기 위한 가상 예시**다. 실제 파일 구조는 Nezha 원본을 확인한 뒤 결정한다.

```json
{
  "incident_id": "incident_001",
  "root_cause_service": "productcatalogservice",
  "cause_line_indices": [12],
  "evidence_line_indices": [13],
  "mapping_status": "success"
}
```

- 줄 번호는 **전처리한 로그에서 0부터 시작하는 인덱스**로 통일하고, 원본 파일의 행과 어떻게 연결되는지 기록한다.
- 공식 자료에 서비스 이름만 있다면 그 서비스의 모든 줄을 원인 GT로 취급하지 않는다.
- 실제 원인·증거 줄을 확인할 근거가 부족하면 `ambiguous` 또는 `not_found`로 남긴다.
