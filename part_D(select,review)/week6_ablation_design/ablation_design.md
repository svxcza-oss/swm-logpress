# LogPress Ablation 설계 (확정 · 후처리 구조)

> 목적: 각 신호가 **압축기 안에서 원인 보존에 실제로 기여하는지**를 하나씩 떼어 확인한다.
> 상태: "어텐션으로 먼저 거르고, 위치·템플릿·시간으로 **후처리**"

---

## 1. ablation이 답하려는 질문

> "위치를 빼면 / 템플릿을 빼면 / 시간을 빼면 / 어텐션을 빼면 — **압축 후 원인 줄 보존율이 떨어지나?**"

떨어지면 그 신호가 **기여한 것**, 안 떨어지면 **기여 안 한 것**. 이게 "각 신호가 실제로 일하나"의 증거.

---

## 2. 설계 원칙 (2개)

1. **한 번에 하나만 바꾼다.** 두 개를 동시에 빼면 보존율이 떨어져도 "둘 중 누구 때문"인지 못 잡는다. 그래서 leave-one-out(전체에서 하나씩 빼기).
2. **기준점(전체)을 두고 비교한다.** "전체 vs 전체−위치"처럼 딱 하나만 다르게 해서, 차이를 그 신호에 귀속시킨다.

---

## 3. 조합표 (확정 · 후처리 구조)

구조: **[어텐션으로 줄 거르기] → [위치·템플릿·시간으로 후처리 재조정]**.
그래서 ablation은 "후처리 신호를 하나씩 얹으며 보존율이 오르나"를 본다. 기준점은 **후처리 없는 어텐션만(B0)**.

| ID | 구성 | 후처리 신호 | 답하는 질문 |
|---|---|---|---|
| **B0** | 어텐션만 (후처리 없음) | — | **기준점** — 후처리 전 순수 어텐션 성능 |
| **B1** | 어텐션 + 위치 후처리 | 위치 | **위치 후처리가 보존을 올리나** (킬스위치 연장) |
| **B2** | 어텐션 + 템플릿 후처리 | 템플릿 | 템플릿 후처리가 올리나 |
| **B3** | 어텐션 + 시간 후처리 | 시간 | 시간 후처리가 올리나 |
| **B4** | 어텐션 + 위치·템플릿·시간 전부 | 3개 | 후처리 다 넣으면 (최종 성능) |

### 읽는 법
- **B0 → B1/B2/B3:** 어텐션 기준에서 신호 하나씩 얹어, 각 신호의 **단독 기여**를 본다. (한 번에 하나만 얹음 = 원칙 1)
- **B0 vs B4:** 후처리를 아예 안 한 것 vs 다 한 것 = **후처리 전체의 효과.**
- **B4 − (B1/B2/B3):** 다 넣은 것에서 하나씩 빠졌을 때와 비교하면 **상호작용**도 볼 수 있음(여유 되면).

### 위치를 미는 핵심
- **B1(어텐션+위치)이 B0(어텐션만)보다 유의하게 높으면** → "위치 후처리가 원인 보존을 실제로 끌어올린다" = 킬스위치(위치가 원인을 구별한다)의 **보존 단계 연장 증거.** 이게 이 ablation의 주인공 결과.

---

## 4. 킬스위치 AUC와 무엇이 다른가 (혼동 방지 — 발표에서 물어봄)

| | 킬스위치 AUC | 이 ablation |
|---|---|---|
| 재는 것 | 신호의 **구별력** (원인 vs 정상) | 신호의 **보존 기여** |
| 압축 | 없음 (원본에서 신호만) | **있음** (압축 후 결과) |
| 질문 | "원인을 구별하나?" | "압축해도 원인을 남기나?" |
| 비유 | 점수를 잘 주나 | 그 점수로 잘라도 살아남나 |

→ 킬스위치는 **재료 검증**("이 신호 쓸 만하다"), ablation은 **완성품 검증**("그 신호가 압축기에서 일하나"). 재료가 좋아도 요리가 되는 건 아니므로 **둘 다 필요**.

---

## 5. 각 조합을 어떻게 채점하나 (기존 코드 재활용)

- **보존율** = 저번 주에 만든 KPI(평가) 코드 그대로.
- **비교·검정** = McNemar (엇갈린 쌍) + BH 보정 (여러 조합이라 가짜 양성 통제).
- ablation이 추가하는 건 = "**조합별로 압축기를 돌리는 반복문**" 하나. 새 큰 코드 아님.
- 압축률(50~90%)마다 각 조합의 보존율을 재서 **곡선**으로 비교.
