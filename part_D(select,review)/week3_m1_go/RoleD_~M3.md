## 1. 보존율 채점기 — "중요한 줄이 살아남았나 채점하기"

### 역할 분담
- **C:** 실제 압축기(LogPress)를 만든다 → 토큰을 버린다.
- **D(나):** 같은 규칙으로 "뭐가 남았나"를 재현해서 → 정답지와 비교 → 보존율 점수를 낸다.
- 둘이 **점수 규칙을 공유**해야 내 재현이 C의 실제 동작과 일치한다.

# 위치는 정답태그를 정하는게 아니다.(alert 사용)
> "alert 태그로 원인을 먼저 정하고
                → 그 원인들 중에 위치가 중간(0.25~0.75)인 것만 골라 본다"
                (원인은 태그로 정해졌고, 위치는 그냥 분류 잣대)

### 전체 흐름
```
C가 만든 압축 규칙 → 내가 코드로 똑같이 옮김 → "이 토큰들이 남았겠다" 계산
→ 남은 토큰 ↔ 정답지(원인 줄) 비교 → 원인 줄 살았나 채점

정답지: "3번 줄 원인" → 표 보고 변환 → "12,13,14,15번 토큰이 원인"
남은 토큰: [12번][15번]... → 12번 살아있네 → 원인 보존 ✅ (하나라도 살면 보존)
```

### 내가 해야 할 것
- **정답지(alert 태그) 확보** — 채점용 답안지. 압축기는 절대 못 본다(순환 방지).
- **C가 만든 압축기의 원리를 모방해서 코드로 재현** — kvpress는 "남은 토큰 목록"을 API로 안 준다. `score()` 로직을 그대로 재현해 상위 `n_kept = int(seq_len * (1 - 압축률))` 개를 numpy로 직접 뽑는다.
- **정답지와 비교해서 보존율 도출.**

### 준비할 재료 3개
1. **줄 ↔ 토큰 번역 표** (`build_line_token_map`) — 정답지는 줄 단위, 압축은 토큰 단위라 단위가 다름. 이어주는 표가 필요.
2. **남은 토큰 목록** — C 규칙 베껴서 계산.
3. **정답지** — 이미 있음. 1번 표로 토큰 번호로 변환해 둠.

### 줄↔토큰 표 만드는 법 (함정 주의)
- 줄을 **하나씩 따로** 쪼개면 안 됨. 모델은 **뭉치 전체를 이어붙여 통째로** 쪼개서 읽는다.
- 방법: `offsets_mapping`으로 각 토큰의 "원문 글자 번호"를 받아 → 각 줄의 글자 범위와 대조 → 어느 줄 소속인지 도장.
- 예외: 줄 경계 걸치는 토큰(규칙 하나 정함), 빈 줄(토큰 0개면 건너뜀), 숫자·경로 분절(글자 번호 있으니 문제없음).

### 뭉치 시작점 기준
- **정각 단위(시계 기준 고정 격자)로 쪼갬** → 한 시간 안에서 위치를 보면 됨.
- 원인 중심으로 자르면 원인이 항상 0.5에 와서 순환이 생기므로, 일부러 정각으로 자름.
- **시간 정보는 이미 로그 줄에 다 표시되어 있음**(시각·노드·줄번호). 채점용 꼬리표는 안 사라진다.

> ⚠️ 이게 4개 중 **제일 무겁고 중요한** 작업. 한 칸 밀리면 모든 보존율 숫자가 틀어진다.

## 2. AI에게 낼 객관식 문제 만들기 (Nezha 기준)

### 왜 객관식인가
- 주관식이면 작은 LLM이 다 빵점(floor) → 압축 방법 간 우열이 안 갈림.
- 객관식으로 바닥을 띄우고, **O/X로 깔끔하게 채점**하려고.

### 문제 수를 몇 개 낼 것인가?
- Nezha 데이터셋을 보고 **원인(사건)이 몇 개인가**를 확인 → 검정력 분석처럼 기준을 세운다.
- 핵심: 총 문제 수보다 **두 방식이 답이 갈린 문제(불일치쌍)**가 중요.
- 목표: 불일치쌍 40~50개 → 총 문제 대략 **150~250개**.
- 단, **Nezha는 작아서** 실제론 "있는 만큼 쓰고 정직하게 보고"가 될 수 있음.
- M1의 300처럼 미리 못 박힌 숫자가 아직 없음 → **지금 미니 검정력 분석 + B와 규모 확인으로 정한다.**
- 이건 **생사 관문이 아님** — 부족하면 Tier-1(보존율)로 방어.

### 선택지 개수(K)?
- 너무 적지도 많지도 않게. 2개는 찍기 50%라 안 됨. **K = 4~5** 권장(찍기 20~25%).
- K는 "원인 종류 수"가 아니라 **문제 하나당 보기 개수**. 원인은 수백 개여도 됨.

### 선택지는 지어내면 안 됨 (기존 오류에서 선택)
```
문제: (A장애 로그) 원인은?
  ① disk I/O error   ← A의 진짜 원인 (정답)
  ② memory leak      ← 다른 장애 B의 진짜 원인
  ③ network timeout  ← 다른 장애 C의 진짜 원인
  ④ CPU throttling   ← 다른 장애 D의 진짜 원인
```
- 또는 그 장애 로그 뭉치 안의 다른 이상해 보이는 줄들을 오답으로 → "로그를 제대로 읽고 진짜 원인을 골랐나"를 정확히 잼.

### 규칙으로 못 박아둘 것 (지어내기 원천 차단)
- 오답은 **Nezha에 실제 존재하는 원인 라벨 풀에서만** 뽑는다 (창작 금지).
- 뽑는 건 **고정 seed로 무작위** (내 취향 개입 차단).
- 정답이 실수로 오답에 또 안 들어가게 (중복 제거).
- 너무 비슷한 원인끼리 안 겹치게 거르는 규칙 (같은 카테고리 중복 방지) — 넣을지는 팀이 결정.
- **정답 위치(①~⑤)도 무작위 셔플** — "정답은 항상 ①" 패턴을 모델이 눈치채지 못하게.
- **로그(지문)만 압축, 문제·보기는 압축 금지.**

### 채점 방법
- **부분점수 없음.** 문제당 맞음(1)/틀림(0)만 기록.
- 이유: **주관 차단 + 재현성 + McNemar 검정**을 위해 일부러 단순하게.
- "총점"은 그냥 보는 게 아니라 **두 방식의 O/X를 문제별로 짝지어** 델타 + 짝진 검정으로 비교.

### McNemar 검정
- **"같은 문제를 두 방식이 풀었을 때, 의견이 갈린 문제에서 우리 방식이 동전 던지기보다 유의하게 많이 이겼나"**를 보는 짝진 검정.
- 둘 다 맞거나 둘 다 틀린 문제는 버리고, **갈린 것(불일치쌍)만** 세서 판정.
- 불일치쌍 < 25면 `exact=True`로 전환.
- 이름의 유래: **맥니마(Quinn McNemar) 씨가 1947년에 만든 검정.** 뜻 있는 단어가 아니라 사람 이름.

## 3. 실험 계획서(ablation) 만들기

> **ablation = 부품 하나씩 빼보며 "이게 진짜 중요했나" 확인하는 실험.** (라면에서 계란 빼보기)
> 지금 할 일은 **설계(계획)만** — 실행은 M5. 3개 중 제일 가벼움.

### 비교 3종

| # | 뭘 바꿔보나 | 뭘 증명(방어)하려고 |
|---|---|---|
| ① | **적용 시점**: 초기 레이어 통과 후 압축(FastKV식) vs 레이어 0부터 vs 층별 차등 | "앞부분 봐주기"가 옳다 = lost-in-the-middle 완화 = 설계 정당성 |
| ② | **입력 필터 vs KV 압축** | §2.1 도구 정당성 (왜 KV를 건드리냐) |
| ③ | **필터+KV 직렬 vs KV 단독** | 회장의 "두 개 구현" 제안에 대한 답 |

### 지금 할 일 (여유 구간)
- **표 3줄 채우기** — 비교 대상 + 각각 어떤 압축률·데이터·지표로 잴지. ✅ 간단
- **①번은 C와 "구현 가능한지" 15분 확인** — 레이어별 압축 시점은 C 코드 영역. ✅ 간단
- **문서에 못 박고 팀 커밋.** ✅ 간단

> 미리 못 박는 이유: 결과 보고 실험 추가하면 p-해킹. M1 판정식 동결과 같은 논리.

## 4. B에게 매주 확인 작업 — Nezha 처리 감시

### B의 작업 목적
- Thunderbird는 "이상(anomaly)"까지만 알려주고 **"진짜 원인(root cause)"은 안 알려줌.**
- Nezha는 **원인 정답이 붙은 유일한 데이터** → 2층 평가(결정타)의 유일한 원료 = 내 객관식 문제의 재료.
- B가 Nezha 원인 라벨을 **구문/코드영역 단위 → 줄 단위로 손수 옮기는 작업**을 한다. 손작업이라 실수 나면 정답지 전체가 티 없이 오염됨 → 방치 금지.

### 매주 15분, 내가 확인할 3가지
1. **정답이 진짜 맞는 줄을 가리키나 (라벨 정합성)** — 5~10개 뽑아 원본과 대조. 제일 중요.
2. **데이터를 '장애 사건' 단위로 나눴나 (누수 방지)** — 같은 사건 줄이 학습용/시험용에 갈라지면 커닝. 반드시 사건 통째로 한쪽에만.
3. **원인 줄이 사건당 몇 개, 총 몇 건 (규모)** — 문제 수 상한선. 검정력 계산의 근거.

### 타임라인
| 시점 | 무슨 일 |
|---|---|
| 3주차 | B가 Nezha 착수 (Baseline 재현과 병렬) |
| ~11주차 | Nezha 완료 = **관문 M-N** |
| 11주차 말 | B → D 핸드오프 (M6 2층 평가의 전제) |
| 12주차~ | D가 평가셋으로 Tier-2 시작 |

- **3주차 착수 → 11주차 완료, 약 8주짜리 긴 병렬 작업.** 그 8주 내내 D가 매주 감시.
- 지금(8월 초)이 딱 착수 시점. AUC 평가 끝났으니 본격 시작.

### ⚠️ A+B 겸직 상황 주의
- 지금 팀은 **A(Baseline 재현) + B(Nezha)를 한 사람이 겸직.**
- 위험 구간 = **3~6주차** (Baseline과 Nezha 시작이 겹침).
- 탈출 전략 = Baseline을 3~6주에 몰아서 끝내고 → 7주부터 Nezha 단독.
- Baseline은 눈에 보이는 결과라 손이 그쪽으로 쏠리고 Nezha가 밀리기 쉬움 → **D 감시가 평소보다 더 중요.**
- **Nezha 최소 슬라이스 조기 확보**(6주차쯤 20~30개 미니 버전) 권장 → 밀림 리스크 분산.

## 주차별 타임라인 — 매주 D가 할 수 있는 것

> 기준점: 지금 대략 **3~4주차** (Nezha 인계 8/3, AUC 평가 완료).
> 이 구간(4~9주)이 D의 여유 구간 = 무기 제작 구간. M3(9주, C 담당) 뒤에 올 M5를 위한 도구를 여기서 다 만든다.

### 매주 고정 루틴 (아래 표와 별개로 항상)
- **Nezha 15분 감시** (정합성·누수·규모) — 3주차~11주차 내내. **A+B 겸직이라 특히 3~6주에 밀리기 쉬움 → 이 구간 감시 최우선.**
- seed·split·감사 로그 커밋 확인.
- 3대 관문(M1·M3·M-N) 리스크 신호등 갱신.

### 주차별 작업

| 주차 | 이번 주 할 수 있는 것 | 산출물 |
|---|---|---|
| **3~4주 (지금)** | ① C와 **점수 규칙·인터페이스(`line_token_spans` 포맷) 합의 회의**<br>② JIT 학습: kvpress `score()` 로직 · forward hook · `offsets_mapping`<br>③ **정각 뭉치 추출 함수** 착수 (원본 → 노드+1시간 뭉치 텍스트+줄 경계) | 인터페이스 합의문, 뭉치 추출 함수 초안 |
| **4~5주** | **줄↔토큰 번역 표** (`build_line_token_map`) 완성 + 단위 테스트<br>(글자 번호 매핑, 줄 경계·빈 줄 예외 처리) | `build_line_token_map` + 테스트 |
| **5~6주** | **남은 토큰 재현** — kvpress 기본 press(Random/H2O 등)로 `score` 재현 → 상위 `n_kept` 뽑기<br>→ `preservation_rate` 완성 → 기본 press로 **end-to-end 채점 리허설** | `preservation_rate`, 채점기 v1 |
| **6주 (분기점)** | **Nezha 최소 슬라이스(20~30개) B한테 받기** ← 조기 확보<br>→ 미니 슬라이스로 채점기 리허설 + 킬스위치 결론 교차 검증<br>**객관식 출제 틀 설계 착수** (규칙 문서화) | 미니 슬라이스, 출제 틀 초안 |
| **6~7주** | **객관식 출제 틀 완성** (오답 뽑기 규칙·고정 seed·정답 셔플·O/X·지문만 압축)<br>**Tier-2 미니 검정력 분석**(McNemar) → 문제 수 목표 확정 + B와 Nezha 규모 확인 | 출제 틀, 문제 수 근거 |
| **7~8주** | **ablation 3종 설계 표** 작성 + **C와 ①번 구현 가능성 15분 확인** + 팀 커밋<br>미니 슬라이스로 문제 틀 검증 → 버그 수정 | ablation 커밋, 검증된 출제 틀 |
| **8~9주** | C의 LogPress 초기본 나오면 → **채점기에 C 점수 규칙 갈아끼우기** 테스트<br>**M3 PoC 주시** (막히기 전에 백업 경로 조기 경보)<br>미니 데이터로 **전체 파이프라인 dry-run** (채점기+문제+통계 한 바퀴) | LogPress 연동 채점기, dry-run 결과 |
| **9주 (M3 관문)** | M3 GO/NO-GO 관여<br>여유 구간 산출물 최종 점검: **채점기 완성 · 출제 틀 완성 · ablation 커밋 완료** | 무기 3종 완성 확인 |

### 9주 이후 (만들어둔 무기를 쓰는 구간)

| 주차 | 무슨 일 |
|---|---|
| **10~13주 (M5, D 오너)** | Tier-1 보존율 평가. **채점기에 데이터 붓기만** 하면 됨 (이미 완성) → 층화 보존율 곡선 |
| **11주 (M-N 관문)** | B → D **Nezha 전체 핸드오프**. 완성된 출제 틀에 데이터 부어 문제 대량 생산 |

| **13~16주 (M7)** | 마무리·논문 총괄 |

> **핵심:** 문제 출제는 **틀(지금~7주) → 미니 리허설(6주) → 대량 생산(11주 핸드오프 후)** 3단계로 나뉜다.
