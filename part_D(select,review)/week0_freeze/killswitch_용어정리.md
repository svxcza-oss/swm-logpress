# 킬스위치 개념 정리

> LogPress 킬스위치(관문 ①)를 이해하는 데 필요한 개념만 모은 문서.
> 프리즈 문서를 읽기 전에 이것부터 보면 된다.

---

## 0. 한 장 요약

**프로젝트가 하려는 것**
서버 장애가 나면 로그가 수백만 줄 쏟아진다. AI한테 "원인이 뭐야?"라고 묻고 싶은데 다 넣을 수가 없다. 줄여서 넣어야 하는데 **줄이다가 진짜 원인 줄을 버리면 AI가 못 맞힌다.** 그래서 "버릴 때 원인 줄은 살려두는 방법"을 만드는 것.

**킬스위치가 하는 것**
원인 줄을 살리려면 **어느 줄이 원인인지 눈치챌 수 있어야** 한다. 그게 되는지 3주차에 확인하고, 안 되면 접는다. 비상정지 버튼.

**킬스위치의 질문 한 줄**
> 희귀도·위치 신호로 원인 줄을 찾아낼 수 있는가?

# 1. 판정에 쓰는 개념

### AUC (Area Under the Curve)
원인 줄 하나와 평범한 줄 하나를 무작위로 집었을 때, **원인 줄 점수가 더 높을 확률.**

| 값 | 뜻 |
| --- | --- |
| 0.5 | 동전 던지기 = 구분 못 함 |
| 0.65 | 65% 확률로 원인이 더 높음 (우리 기준선) |
| 1.0 | 항상 맞힘 |

### 양성 / 음성
- **양성(positive)** = 원인인 줄 = 하드케이스
- **음성(negative)** = 평범한 줄

AUC는 이 둘을 **섞어놓고 점수로 줄 세우는** 것이라 **양쪽 다 있어야** 계산된다. 음성 없이는 AUC 자체가 안 나온다.

### H₀ / H₁ (귀무가설 / 대립가설)
- **H₀:** "신호가 쓸모없다" (AUC = 0.5) ← 이걸 깨는 게 목표
- **H₁:** "신호가 쓸모있다" (AUC > 0.5) ← 우리 주장

통계는 항상 "쓸모없다"를 먼저 세워두고 그걸 반박하는 방식으로 간다.

### one-sided (단측)
"더 높다" 방향만 본다는 뜻. "다르다"(양측)가 아니라 "더 높다"(단측)로 미리 방향을 정해두면, 나중에 결과 보고 유리한 방향을 고르는 걸 막을 수 있다.

### 검정력 분석
**"차이가 진짜 있다면, 표본 몇 개는 있어야 놓치지 않고 잡아낼까?"**를 계산하는 것.

표본이 적으면 진짜 차이가 있어도 우연인지 아닌지 판정이 안 된다. AUC 0.65를 안정적으로 검출하려면 원인 사례 **30~37개**가 최소선 → 안전 여유를 둬서 **양성 40개**, 전체 **300개**로 잡음.

### 순열검정 (permutation test)
**"이 정도 점수가 우연히 나올 수 있나?"를 직접 실험해보는 방법.**

1. 정답 라벨을 **무작위로 뒤섞는다** (원인/평범을 랜덤 재배치)
2. 그 엉터리 라벨로 AUC를 계산한다
3. **5,000번** 반복
4. 5,000개의 "우연 점수" 분포가 나온다 ← **귀무분포**
5. 진짜 AUC가 그 분포보다 확실히 높으면 → 우연이 아님

**p < 0.05** = 우연히 이 점수가 나올 확률이 5% 미만

**왜 5,000번?** 정확도와 시간의 타협점. p=0.05를 판정할 해상도가 나오면서 시간도 오래 안 걸린다. 그 이상 늘려도 p값은 거의 수렴. **중요한 건 숫자가 아니라 미리 정해서 안 바꾸는 것.**

### 로버스트니스 (robustness)
**튼튼함. 조건을 바꿔 재봐도 결과가 흔들리지 않는 성질.**

```
음성 1개씩 붙여 재니 → AUC 0.68
음성 4개씩 붙여 재니 → AUC 0.67
→ 비슷하네. 믿을 만함 ✅

음성 1개씩 → 0.68
음성 4개씩 → 0.52
→ 왜 이렇게 달라? 못 믿겠음 ❌
```

체중계에 아침·저녁 올라가서 비슷하면 믿을 만한 것과 같은 원리.
**주의:** 1:1을 재고 결과를 본 뒤 1:4를 재면 "유리한 쪽 골랐냐"는 의심을 받는다. **둘을 같은 실행에서 함께 측정**해야 한다.

### 민감도 분석
**조건을 바꿔도 결론이 그대로인지 확인하는 것.** 매칭 실패 70개를 포함했을 때 vs 제외했을 때 결과가 크게 다르면 결론이 취약하다는 뜻.

# 2. 데이터에 관한 개념

### alert 태그
**Thunderbird 제작자가 미리 붙여둔 표시.** 로그 줄 맨 앞 칸에 있다.

```
-        1131523501  tftp: client does not accept options
↑                    ↑
alert 태그            메시지 본문
```

| 맨 앞 칸 값 | 뜻 |
| --- | --- |
| `-` (하이픈) | 정상 |
| `PBS_CON`, `MPT`, `CPU`, `SCSI` 등 | 이상 (원인 후보) |

**핵심:** 우리가 만든 게 아니고 **위치와 무관하게** 붙어 있어서 **정답지로 쓸 수 있다.**

### 템플릿 (Drain3)
로그 문구에서 **매번 바뀌는 부분을 지우고 뼈대만 남긴 것.**

```
node-042 disk sda1 I/O error
node-113 disk sdb2 I/O error   →   node-<*> disk <*> I/O error
node-887 disk sdc1 I/O error
```

Drain3가 이걸 자동으로 묶어준다. 그래서 하드케이스 **14,939줄이 템플릿 9종**으로 정리됨. 겉보기엔 1.5만 줄이지만 **말하는 내용은 9가지뿐.**

### 의사복제
**가짜로 표본이 많아 보이는 현상.**

디스크 고장 1건이 로그에 500줄 찍히면:
- 줄로 세면 → 500개 표본 ← **뻥튀기**
- 실제 사건 → 1개

통계에서 표본 500개면 "충분히 많다"고 믿게 되는데, 사실 정보량은 1건분. 그래서 줄 단위(14,939)를 안 쓰고 **버스트 단위(6,722)**로 센다.

### 버스트 (독립 표본 단위)
의사복제를 막기 위해 **(노드, 템플릿, 5분 시간창)**으로 묶은 덩어리. **이것이 독립 표본 1개.**

같은 노드에서 같은 템플릿이 5분 안에 연달아 나오면 1개, 5분 이상 잠잠했다 재발하면 새로 1개.

| 묶는 기준 | 없으면 생기는 문제 |
| --- | --- |
| **노드** | 다른 서버에서 난 일을 같은 사건으로 착각 |
| **템플릿** | 디스크 에러와 CPU 에러를 한 덩어리로 뭉갬 |
| **5분** | 어제 일과 오늘 일을 같은 사건으로 셈 |

**세는 방법에 따라 개수가 확 달라진다:**

| 세는 방법 | 개수 |
| --- | --- |
| 줄 단위 | 14,939 (뻥튀기) |
| **(노드,템플릿,5분)** | **6,722** ← 채택 |
| 노드별 | 3,085 |
| 문구 종류(템플릿) | 9 (300 미달) |

### 하드케이스
**alert 태그가 붙어 있고 + 본문에 error류 단어가 없는 줄.**

본문에 `error`가 써 있는 줄은 **기존 레벨 필터가 이미 잡는다.** 우리가 노리는 건 "진짜 원인인데 본문엔 error라고 안 써 있어서 기존 방법이 놓치는 줄" — 그래서 **hard**case.

### 레벨 필터 / 보존율
- **레벨 필터** = 기존의 쉬운 방법. 로그에 `error`, `fail` 같은 단어 있으면 남기기
- **보존율** = 레벨 필터를 썼을 때 원인 줄이 얼마나 살아남는가

```
보존율 0.99 이상 → 기존 필터로 원인이 99% 살아남음
                 → 문제가 이미 해결됨 → 우리 도구 필요 없음 ❌
보존율 낮음      → 기존 필터로는 원인이 다 날아감
                 → 우리 도구가 필요함 ✅
```

Thunderbird 하드케이스는 **보존율 0%(100% 미포착)** → 조건 압도적 충족.
이건 **"문제가 진짜 어렵다"는 증명**이다.

### VAPI
alert 태그 중 하나. **322만 줄로 매우 흔하고** 본문에 error류 단어가 있어서 **레벨 필터가 이미 잡는다.** 우리 대상이 아니라서 제외. 하드케이스에는 30줄만 섞여 있어 빼도 영향 없음.

### BGL
**다른 로그 데이터셋 이름.** Thunderbird와 같은 계열(슈퍼컴퓨터 로그). 표본이 부족할 때 합쳐서 늘리는 백업 플랜.

### 층화
**데이터를 그룹으로 나눠서 각각 보는 것.** 표본이 부족하면 하드케이스 기준(non-ERROR)을 느슨하게 해서 더 포함시키는 데 쓴다.

# 3. 신호에 관한 개념

### 희귀도 (rarity)
**이 로그 문구가 전체에서 몇 번 나왔나.** 드물수록 높은 점수.

```
"백업 완료"      → 200만 번  → 희귀도 낮음 → 평범
"SCSI I/O 실패"  → 12번      → 희귀도 높음 → 수상
```

매일 200만 번 찍히는 로그가 오늘 장애의 원인일 리 없다. 거의 안 나오던 게 갑자기 튀어나왔으면 그게 원인일 가능성이 높다.

**한계:** 템플릿마다 값이 **하나로 고정**된다. PBS_CON은 어디서 나오든 항상 같은 희귀도. 양성 템플릿이 9종이니 **희귀도 점수도 9가지밖에 안 나온다.**

### 위치 (position)
로그 뭉치를 **0~1로 놓고** 이 줄이 어디쯤인지. 맨 앞 0, 한가운데 0.5, 맨 끝 1.

**희귀도의 한계를 메꾼다.** 같은 템플릿이라도 버스트마다 위치가 달라서 점수가 촘촘해진다.

### 결합 신호
희귀도 + 위치를 합쳐 만든 점수 하나.

**왜 합치나:** 희귀도만 쓰면 점수가 9가지뿐이라 검정이 뭉툭하다. 위치를 더해야 촘촘해진다.

# 4. 함정을 막는 개념

### 순환 (circularity)
**시험 문제를 내면서 답을 문제에 적어놓는 것.**

```
❌ 순환:
   정답 정의: "중간에 있는 줄 = 원인"
   신호:      "중간에 있으면 원인일 것"
   → 중간이라고 정해놓고 중간으로 맞힘. 당연히 맞음. 의미 없음.

✅ 정상:
   정답 정의: "alert 태그 붙은 줄 = 원인"  (위치 무관)
   신호:      "중간에 있으면 원인일 것"
   → 정답은 위치를 모르는 채로 정해졌고, 신호가 그걸 위치로 맞힘.
```

**해결:** 양성 정의에서 위치 조항을 뺀다. 라벨은 alert 태그로만.

**"59.2%가 중간에 있다"는 왜 괜찮나?**
- 라벨 기준으로 쓰면 ❌ (중간이니까 원인이다 → 위치로 정답을 정함)
- **관측 결과로 쓰면 ✅** (태그로 정답 정했더니 알고 보니 59%가 중간이더라)

순서가 다르다. 후자는 위치가 정답 결정에 개입하지 않았다. → **"위치 신호가 통할 것 같다"는 정황 근거**로만 사용.

### 교란 (confounder)
**진짜 원인이 아닌데 결과에 영향을 주는 요인.**

> "아이스크림 많이 팔린 날 익사 사고가 많다" → 아이스크림이 익사를 부르는 게 아니라 **더위**라는 숨은 요인이 둘 다 올린 것. 여기서 더위가 교란.

**우리 경우:** 원인 줄이 특정 서버·시간대에 몰려 있는데 음성을 딴 서버·딴 시간에서 뽑으면, AUC가 높아도 **"신호가 좋아서"인지 "조건이 달라서"인지 구분 불가.**

**해결:** 음성을 **같은 노드 · ±1시간**에서 뽑는다 = 교란 통제.

### 매칭 (matching)
교란을 통제하려고 **조건은 똑같이 맞추고 라벨은 반대로** 음성을 뽑는 것.

| 항목 | 처리 |
| --- | --- |
| **맞출 것** | 같은 노드, ±1시간 이내 |
| **반대로 둘 것** | 라벨 (양성=원인, 음성=평범) |
| **건드리지 말 것** | **위치** — 측정 대상이라 억지로 맞추면 신호가 죽는다 |

**주의:** 양성과 음성이 "같은 표본"이면 안 된다. **조건만 같고 라벨은 반대**여야 한다.

### 선택 편향 (selection bias)
**표본을 고르는 방식 때문에 결과가 왜곡되는 것.**

키 큰 사람만 골라서 "우리 반 평균 키"를 재는 것과 같다.

**우리 경우:** 매칭 실패한 줄들을 그냥 버리면 안 된다. 그것들은 "주변에 정상 로그가 아예 없는 = 조용하다 갑자기 튄" 케이스라 **하필 가장 원인다운 것들**일 수 있다. 빼고 재면 왜곡된다.

**해결:** 제외 금지, 2단계 폴백 후 민감도 분석에서 별도 보고.

### p-해킹 / optional stopping
**결과가 맘에 들 때까지 계속 시도하는 것.**

- **p-해킹:** 여러 방법으로 돌려보다가 유의하게 나온 것만 보고
- **optional stopping:** p값이 애매하면 표본을 더 모으거나 반복 횟수를 늘려 재시도

```
5,000번 돌림 → p = 0.06 (아깝다)
"10,000번 해볼까?" → p = 0.048 (통과!)
→ 이걸 결과로 씀  ← 가짜
```

**해결:** 순열 5,000회 고정, seed 고정, 규칙 먼저 커밋.

### seed (시드)
컴퓨터의 무작위는 진짜 무작위가 아니라 **시작 숫자(seed)를 넣으면 정해진 순서대로 나오는 계산**이다.

```
random.seed(42)  →  몇 번을 돌려도 항상 똑같은 것들이 뽑힘
```

주사위를 굴리되 **굴리는 방식을 완전히 재현할 수 있게 못박아두는 것.** 무작위의 장점(편향 없이 고르게)은 유지하면서 재현 불가 문제만 없앤다.

**seed를 안 고정하면:** ① 나중에 같은 결과가 안 나와서 재현 불가 ② "좋은 값 나올 때까지 다시 돌리기"의 문이 열림

### 사전등록 (pre-registration)
**데이터를 보기 전에 규칙을 정해놓고 서명·커밋하는 것.**

순서가 핵심이다:
```
규칙 확정 → 4인 서명 → git commit → 해시 기록 → 그 다음에 데이터 접근
```

커밋 해시와 타임스탬프가 **"데이터 보기 전에 정했다"는 증거**가 된다. 결과를 본 뒤 임계값을 바꾸면 모든 검정이 무효.

# 5. 임계값의 출처

| 임계값 | 출처 |
| --- | --- |
| **표본 300 / 양성 40** | ROC 검정력 분석 — Hanley & McNeil (1982), *Radiology* 143(1), 29–36. 소수 클래스 30~37개가 하한, 의사복제 방어로 상향 |
| **AUC 0.65** | 근본 논문 **없음(관례)**. 아래 3단 논리로 방어 |
| **level-filter 0.99** | 관례. "기존 방법으로 다 되면 프로젝트 의미 없음"의 경계선 |
| **순열 5,000회** | 관례. 정확도-시간 타협점 |

### AUC 0.65의 3단 방어 논리

단일 논문이 없어서 셋을 이어붙인다.

**① AUC = Mann-Whitney U 통계량**
> Hanley, J. A. & McNeil, B. J. (1982). "The meaning and use of the area under a receiver operating characteristic (ROC) curve." *Radiology*, 143(1), 29–36.

**② 거기서 `r = 2·AUC − 1`이 나옴**
> Kerby, D. S. (2014). "The simple difference formula: An approach to teaching nonparametric correlation." *Comprehensive Psychology*, 3, 11.IT.3.1.

**③ r = 0.30 = 중간 크기 효과 하한**
> Cohen, J. (1988). *Statistical Power Analysis for the Behavioral Sciences* (2nd ed.). Lawrence Erlbaum. pp. 77–82.
> small 0.10 / **medium 0.30** / large 0.50

**교차 검증**
> Vargha, A. & Delaney, H. D. (2000). *Journal of Educational and Behavioral Statistics*, 25(2), 101–132.
> Vargha-Delaney A(= AUC)에서 **medium ≥ 0.64** → 0.65는 medium 구간

**계산:** `r = 2 × 0.65 − 1 = 0.30` ✅

**주의점 두 가지**
1. `r = 2·AUC − 1`은 엄밀히는 **순위상관**(Cliff's delta, Somers' D, Gini와 동일)인데 Cohen의 0.30은 원래 **Pearson r**용. 관행적 환산임을 인정하는 게 안전.
2. **의학 진단 기준(Hosmer-Lemeshow)에서는 0.65를 "poor"로 분류.** 이걸 먼저 인정하고 "탐색적 로그 RCA는 맥락이 다르다"고 방어해야 한다.

# 6. 자주 헷갈리는 것

### "5분"이 두 개다
| 어느 5분 | 뜻 |
| --- | --- |
| **표본 세는 5분** | (노드, 템플릿, **5분**) — 버스트 묶는 창. 이미 확정 |
| **매칭 시간 범위** | 음성 짝을 찾는 범위 → **±1시간**으로 확정 (5분 아님) |

### "비교군"이 baseline이 아니다
여기서 **비교군 = 음성(non-cause) 표본.** "다른 방법과 성능 비교(baseline)"가 아니라 **"양성 vs 음성 대조"**라는 뜻. 환자군에 대한 **대조군**과 같은 개념.

### 양성과 음성은 "같은 표본"이면 안 된다
맞춰야 하는 건 **라벨이 아니라 교란 조건(노드·시간대)**이다.

| | 양성 | 음성 | 맞춰야 하나 |
| --- | --- | --- | --- |
| 원인 여부 | O | X | ❌ **반대여야 함** |
| 노드·시간대 | 특정 | 같게 | ✅ **맞춰야 함** |
| 위치 | (측정 대상) | (측정 대상) | ❌ 건드리면 안 됨 |

### AUC는 클래스 비율에 영향을 안 받는다
1:1이든 1:100이든 AUC 기댓값은 같다. (정확도(accuracy)는 비율에 크게 흔들리지만 AUC는 순위 기반이라 안 흔들림.)
→ 그래서 **1:4를 하는 이유는 "불균형 재현"이 아니라 "음성 뽑기 운에 의존하지 않음을 보이려는 것"**이다.
