# 1. 가설

원인 줄을 찾는 단서 두 개를 합쳐 점수 하나로 만든 것이 **결합 신호**(희귀도 + 위치). # 4 참고

희귀도(rarity): 이 로그 문구가 전체에서 몇번 나왔나 카운팅, 드물수록 원인일 가능성이 높다는 가설로 전개해 희귀도 측정.
위치: 로그 뭉치를 0~1로 놓고 이 줄이 어디쯤인지, 맨 앞 0, 맨끝 1, 한가운데 0.5

++(둘다 쓰는 이유)희귀도는 템플릿마다 값이 하나로 정해짐. 같은 템플릿이면 어디서 나오든 희귀도가 똑같음.
양성 템플릿이 9종이기 때문에, 희귀도 점수가 9가지밖에 안나옴. 표본은 6,722개인데, 실제로 구별되는 값은 9개.
그래서 위치를 붙임.


| **H₀** | 결합 신호가 원인 줄을 평범한 줄과 구분하지 못한다 (AUC = 0.5, 동전던지기와 같은 확률) |
Auc 0.5가 왜 구분을 못하는거? (Area under the curver, 통계학과 머신러닝에서 분류 모델이 양성(True)과 음성(False)을 얼마나 잘 구별해 내는지 평가하는 핵심 지표)
** 이 문서에서의 auc는 원인 줄 하나, 평범한 줄 하나를 무작위로 집었을대, 원인 줄 점수가 높을 확률 **

| **H₁** | 결합 신호가 원인 줄에 더 높은 점수를 준다 (AUC > 0.5, one-sided, 65%확률로 원인이 더 높음) |
** 왜 0.65인가? **
r = 2*AUC -1
AUC = 0.65 대입
r = 0.30 --> 이 값은 통계학에서 중간크기 효과의 하한선.

| ① 양성(원인인 줄(정답이 '맞다'인것) - hardcase) | 양성 독립단위 ≥ 40 | 40 | **6,722** | ✅ |
| ① 음성(평범한 줄(정답이 '아니다' 인것)) | 음성 독립단위 확보 (매칭 추출) | 양성의 1배 이상 | 매칭 **6,652** · 폴백 **70** | ⚠️ 재추출✅ |

| ②-강건 | **1:4** AUC ≥ 0.65 & 1:1과의 차 ≤ 0.05 | 0.65 | 측정 예정 dmauc |

| 보조 | level-filter 보존율 < 0.99 | 기존의 단순한(error존재 판단)으로는 원인줄 못살림 | 하드케이스 **100% 미포착** | 하드케이스는
단순 레벨필터로 거를수 없다| Thunderbird의 정당성 |

①은 잴 자격을 보장하고, ②는 실제 성능을 잰다. AUC를 여러 조건에서 재봤더니 로버스트인것을 증명해야함.
**②와 ②-강건은 같은 실행에서 함께 측정한다.** 1:1을 재고 결과를 본 뒤 1:4를 재면 유리한 쪽을 골랐다는 의심을 피할 수 없다. 두 조건에서 재본 AUC가 비슷하면 결과가 표본 비율에 흔들리지 않는다는 뜻이다(로버스트).

# 3. 라벨 vs 신호 (순환 방지)__ 정말 해결되는것인가?

순환? 시험문제를 내면서 답을 문제에 적어놓은것.

| **채점 기준 (정답 라벨)** | alert 태그만 기준선정 | ❌ 제외 | + alert 태그는 로그줄 앞에 붙어있는 "-" or "PBS_CON", "SCSI", "CPU" 등등
| **정답을 맞추는 신호** | 희귀도 + 위치 | ✅ 포함 |

- 이전 판의 양성 정의 "(b) 중앙 위치(0.25~0.75)" 조항 **삭제** → 순환 차단.
정답 정의 : "중간에 있는 줄 = 원인"
신호 : "중간에 있으면 원인일 것"
--> 이렇게 정답을 맞춘다면 의미가 없을것.(답을 미리 정하고 들어가는꼴)

이러한 순환방지를 위해 위치 제거.

- 데이터 검증: `is_anomaly`/`is_hardcase`가 `alert_tag`로 완전 결정, `position_ratio`는 라벨 규칙에 미포함(예외 0건).
- **"59.2% 중간 집중"은 라벨이 아니라 관측 결과** — 위치 신호가 통할 것이라는 정황 근거로만 사용.


(alert태그 == "-"(정상) or "PBS_CON", "SCSI", "CPU"(이상) 등등, thunderbird에서 하이픈이 있으면 정상, 없으면 이상로그줄, 이건 thunderbird만든 사람이 미리 붙여둔 태그이기 때문에 위치와 아무 상관이 없고, 이상로그를 잡는 기준이 될수 있음. 태그가 있는것은 원인줄이라는것.)
정답: "태그 붙은 줄 = 원인"(위치 상관없음)
신호: "중간에 있으면 원인일 것"
--> 정답은 위치를 모른채 정해졌고, 신호가 그걸로 위치를 맞히는것.

# 4. 신호 정의

| **희귀도(rarity)** | 템플릿이 전체 로그에서 몇 번 나왔는가. 드물수록 높은 점수 | 템플릿당 1개 → **9가지 한계** |
이 로그 문구가 전체에서 몇번 나왔나 카운팅, 드물수록 원인일 가능성이 높다는 가설로 전개해 희귀도 측정.
| **위치** | 로그 뭉치 0~1 기준 상대 위치 (앞 0, 중앙 0.5, 끝 1) | 버스트마다 달라짐 |

**결합 이유:** ++(둘다 쓰는 이유)희귀도는 템플릿마다 값이 하나로 정해짐. 같은 템플릿이면 어디서 나오든 희귀도가 똑같음.
양성 템플릿이 9종이기 때문에, 희귀도 점수가 9가지밖에 안나옴. 표본은 6,722개인데, 실제로 구별되는 값은 9개.
그래서 위치를 붙임.

**잔여 리스크:** 위치 신호는 "중간=원인" 가정이 데이터 의존적. 실측 AUC가 낮으면 NO-GO 대응으로 이행.

# 5. 표본 단위

**(노드, 템플릿, 5분 시간창) 하나 = 독립 표본 1개.** 같은 노드에서 같은 템플릿이 5분 안에 연달아 나오면 1개, 5분 이상 잠잠했다 재발하면 새로 1개.
템플릿?
로그 문구에서 변하는 부분을 지우고 뼈대만 남긴것. (drain3 이용, 겉보기엔 1.5만줄이지만 말하는 내용은 9가지뿐인것.)


| 기준 | 없으면 |
| --- | --- |
| 노드 | 다른 서버 일을 같은 사건으로 착각 |
| 템플릿 | 디스크 에러와 CPU 에러를 뭉갬 |
| 5분 | 어제 일과 오늘 일을 같은 사건으로 셈 |

- **실측 6,722개.** ±1시간 매칭 성공 6,652, 실패 70.
- **제외:** CHK_DSK 13개(단일 노드 전용), `#N#` 31개(플레이스홀더 → 노드 매칭 불가). 사유·개수 기록.
이 세개가 모두 같아야 "같은 사건"으로 판정. 하나라도 다르면 별개의 표본.
템플릿을 넣으면 표본이 늘어남.

# 8. 음성 & 매칭 규칙

**현행 비교군 파일 부적합 → 재추출.** 무작위 균등 추출로 확인됨(position 0~1 균등, 시간 8개월 전 구간, 노드 3,876개로 불일치).

| 항목 | 처리 |
| --- | --- |
| **맞출 것** | 같은 노드, **±1시간 이내** |
| **반대로 둘 것** | 음성은 alert 태그 `-`인 non-cause |
| **건드리지 말 것** | **position 매칭 금지** (측정 대상이라 맞추면 신호가 죽음) |
| **세는 단위** | 양성과 동일 (노드, 템플릿, 5분) |
| **비율** | **1:4 중첩 추출** — 양성 1개당 음성 4개를 뽑되 **첫 번째가 1:1용**. 따로 뽑으면 두 집합이 달라져 비교가 성립하지 않음 |
| **음성 내 ERROR** | non-ERROR(INFO)로 한정 (현행 파일에 1,896개 혼입) |
| **후보 선택** | ±1시간 창 내 무작위 추출 |

**"가장 가까운 것"을 안 쓰는 이유:** 음성이 양성 직전·직후 라인이 되어 같은 장애에 오염될 수 있음. 교란 통제는 창 자체가 보장.

### 시간 범위 = ±1시간 (실측 근거)

| 범위 | 성공 | 실패 |
| --- | --- | --- |
| 같은 5분 | 14,478 (96.9%) | **461** |
| ±30분 | 14,846 (99.4%) | 93 |
| **±1시간** | **14,869 (99.5%)** | **70** |
| ±6시간+ | 14,939 (100%) | 0 |

- **같은 5분 탈락:** 실패 461개가 "정상 로그 없이 갑자기 튄" 케이스라 가장 원인다울 수 있음.
- **±6시간+ 탈락:** 결과는 같은데 교란 통제만 느슨해짐.

### 매칭 실패 = 제외 금지, 2단계 폴백

1. ±1시간 · 같은 노드 매칭
2. 실패 시 → 같은 노드 **전체 기간**으로 시간 제약만 완화
3. 그래도 실패 → 제외하지 말고 **민감도 분석에서 별도 집계·보고**

### 레벨필터 ERROR를 음성으로 안 쓰는 이유
"숨은 원인 vs 뻔한 에러"를 묻게 되어 킬스위치 질문과 어긋나고, rarity가 자동으로 갈려 AUC가 부풀려짐. 서술적 근거로만 사용.

# 10. 임계값 근거

| 임계값 | 근거 |
| --- | --- |
| **표본 300** | ROC 검정력(Hanley-McNeil 1982)상 소수 클래스 30~37개가 하한. 의사복제 방어로 300 보수 설정 |
| **양성 40** | 검정력의 실제 결정 요인은 소수 클래스 수. 단 **템플릿 단위(9종)로는 미달**이므로 (노드,템플릿,5분) 단위 사용이 전제 |

*측정 출처: Thunderbird 전체 2억 1,121만 줄 전수 스캔(2005-11-11 ~ 2006-07-11, 243일), B트랙, parse error 0.*
*비교군 검증: `killswitch_comparison_normal.csv`(14,939행) = 무작위 균등 추출 → 재추출 대상.*

AUC는 Mann-Whitney U와 동치이며(Hanley & McNeil, 1982), rank-biserial 상관으로 r = 2·AUC − 1로 환산된다(Kerby, 2014). AUC 0.65 → r = 0.30으로, Cohen(1988)의 중간 크기 효과 하한과 일치한다. Vargha-Delaney A 기준(medium ≥ 0.64)으로도 medium 구간에 속한다(Vargha & Delaney, 2000).
r = 2·AUC − 1은 엄밀히는 순위상관(Cliff's delta, Somers' D, Gini와 같은 값)인데, Cohen의 0.30 기준은 원래 Pearson r용입니다. 순위상관에 Pearson 기준을 적용하는 건 흔한 관행이지만 엄밀히는 근사. 관행적 근사라는것을 인정하는것이 중요.
