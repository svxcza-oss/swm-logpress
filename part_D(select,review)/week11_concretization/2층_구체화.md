## 2. 무엇을 정확히 재나 (측정 대상 + 방법)

| 지표 | 측정 방법 | 단위 |
|---|---|---|
| KV 메모리 | 이론 계산, GPU 피크 실측 | GB |
| TTFT | 실측 (시계로만 가능) | ms |
| throughput | 실측 | tokens/sec |
| inference time | 실측 | s |

- 비교 대상(무엇 대비 잴 것): 압축, baseline별
- 참고: 시간 계열(TTFT·throughput·inference)은 **실측만 가능**(계산 불가). KV 메모리만 `2 × 레이어수 × KV헤드수 × head_dim × 토큰수 × 바이트수` 공식으로 이론 계산도 됨 → 추천: **둘 다**(이론으로 순수 KV 절감, 실측으로 실제 확인).
- 단위 참고: TTFT는 ms, inference time은 s, throughput은 tokens/sec(고정), KV 메모리는 GB. **"실측"은 사람이 초시계로 재는 게 아니라 코드가 `time.time()`으로 자동 기록**하는 것. 표기 단위(ms vs s)는 정밀도와 무관 — 읽기 편한 쪽으로.

### 실측 코드 예시 (개념용 — 실제는 조건별 반복)

```python
import time, torch

def measure(model, input_ids):
    torch.cuda.reset_peak_memory_stats()      # 메모리 측정 초기화
    torch.cuda.synchronize()                   # GPU 작업 동기화(정확한 시간 위해)
    start = time.time()

    first_token_time = None
    generated = 0
    for step, tok in enumerate(model.generate_stream(input_ids)):   # 토큰 하나씩
        if step == 0:
            torch.cuda.synchronize()
            first_token_time = time.time()      # ← 첫 토큰 나온 순간 = TTFT 기준
        generated += 1

    torch.cuda.synchronize()
    end = time.time()

    ttft            = (first_token_time - start) * 1000             # ms
    inference_time  = end - start                                   # s
    throughput      = generated / (end - first_token_time)          # tokens/sec
    kv_mem_gb       = torch.cuda.max_memory_allocated() / 1024**3    # GB (실측 피크)

    return ttft, inference_time, throughput, kv_mem_gb

# 조건별(압축률·모델·컨텍스트 길이)로 N회 반복 → 첫 회 버리고 평균±표준편차
```

- 핵심: `torch.cuda.synchronize()`로 GPU 작업이 진짜 끝난 시점을 잡아야 시간이 정확 (안 하면 GPU가 비동기라 잘못 측정됨).
- 실제 코드는 압축기별로 이 `measure()`를 돌려 비교. (담당: 민규님 — 평가 맞춘 코드)

## 3. 핵심 지표 — 원본 원인(G) 단위당 절감 (계산식 확정)

```
원인당 메모리 절감 = (무압축 KV메모리 − 압축 KV메모리) / |G|
원인당 지연 절감   = (무압축 지연 − 압축 지연)       / |G|
```

- **분모 = |G| = 원본의 전체 원인 라인 수** (그라운드 트루스). ← "압축 후 보존한 수"가 **아님**.
  - 이유: 분모가 **모든 압축기에 동일한 고정값**이어야 공정 비교가 됨. "각자 보존한 수"로 하면 분모가 달라져 비교 불가 + 덜 보존한 쪽이 유리해 보이는 역설 발생.
- 명칭 주의: "retained evidence 단위당"이 아니라 **"원본 원인(G) 단위당"**이 정확 (분모가 원본 G라서).

## 4. 어텐션 추출 비용 처리

- **방침: forward 비용은 공통 소거.** baseline(SnapKV·H2O 등)도 우리도 어텐션을 위해 forward를 1회 수행 → **forward는 양쪽 공통 비용이라 비교에서 빠진다**(= 1층 McNemar에서 공통분 a·d를 빼는 것과 같은 원리).
- 따라서 비교 대상 = **forward 위에 각자 추가로 드는 연산만.** 우리 쪽 추가분 = 로그신호 계산(레벨·희귀도·위치)인데 파싱·카운트라 forward 대비 미미.

```
순절감 = (압축으로 아낀 메모리·지연) − (forward 위에 우리가 추가로 쓴 비용)
         └ forward 자체는 양쪽 공통이라 이 식에서 소거됨
```

- **판정 방식:** forward 공통 소거 후, 남는 추가 비용보다 압축 이득이 크면 OK → 5번 파레토 비교에 그대로 반영.
- ⚠️ 예외 체크: 우리가 forward를 **더 많이** 돌리면(예: output sensitivity 재려고 라인마다 재-forward) 그건 공통 아님 → 그 부분만 별도 계산. `____` (해당되면 명시)

## 5. 합격 기준

**판정 방식:** 보존율과 비용, 두 가지를 같이 놓고 본다. **둘 다에서 baseline보다 나쁘지 않으면서, 최소 하나에서 확실히 이기면 성공** (= 파레토 우위).

**쉽게 말하면:** "우리가 원인을 더 잘 보존하거나(품질 승) / 더 싸거나(비용 승) — 둘 중 하나라도 이기고, 나머지에서 지지 않으면" 합격.

**세 가지 이기는 경우 (다 성공으로 인정):**
- 더 잘 보존하면서 + 더 싸다 → 완승
- 보존율은 같은데 + 더 싸다 → 성공
- 비용은 같은데 + 더 보존한다 → 성공

**강조용 (결과 잘 나오면):** "원인 보존율 `____`%를 맞추는 데, 우리는 압축률 `____`%까지 가능한데 baseline은 `____`%밖에 못 간다 = 같은 품질을 더 싸게 낸다."

**통계 보조:** 여러 번 측정한 값이 흔들리지 않는지 부트스트랩 신뢰구간으로 확인.
